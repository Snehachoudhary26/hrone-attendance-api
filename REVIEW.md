# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health` (lines 72-74) | Returns `{"status": "ok"}` statically without verifying MongoDB connection. Spec requires 200 only if MongoDB answers a ping, else 503. | Stopping MongoDB daemon and calling `GET /health` still returned 200 OK instead of 503 Service Unavailable. | Added `client.admin.command("ping")` within try-except; raises HTTP 503 if ping fails. |
| 2 | `compute_late_minutes` (lines 33-37) | Incorrect grace period evaluation. Uses integer division `minutes = int((punch_in - start).total_seconds() / 60)` and checks `minutes > 10`. R2 specifies late if strictly > 10:00 (600s) after shift start, then floor minutes since shift start. | A punch-in at 09:40:01 for a 09:30 shift (601 seconds elapsed) evaluated `minutes = 10`, returning 0 instead of 10. | Changed condition to check `elapsed_seconds > 600`, then returning `int(math.floor(elapsed_seconds / 60))`. |
| 3 | `compute_late_minutes` / `compute_overtime` (lines 35, 46) | Timezone mismatch and naive/aware datetime arithmetic. Mutates datetime directly without ensuring proper conversion between UTC instants and IST (`UTC+05:30`). | Comparing naive BSON/UTC timestamps against IST shift datetimes raises `TypeError` or gives skewed offsets. | Explicitly converted all timestamps to IST timezone (`UTC+05:30`) before date and time component calculations. |
| 4 | `compute_overtime` (line 47) | Ignores the 30-minute minimum threshold mandated by Rule R3. | Punching out 15 minutes after shift end returned 15 overtime minutes instead of 0. | Added threshold check: return `overtime_minutes` only if `>= 30`, otherwise return 0. |
| 5 | `compute_overtime` (lines 44-47) | Fails on overnight shifts (e.g., 22:00 to 06:00). Sets shift end on the same calendar day rather than the next day. | For shift 22:00-06:00 on date `2026-07-06`, punch-out at 06:40 on `2026-07-07` was compared against `2026-07-06 06:00`, yielding 1480+ overtime minutes. | If `shift_end <= shift_start`, shift end datetime is advanced by 1 calendar day (`+ timedelta(days=1)`). |
| 6 | `compute_work_hours` (lines 40-41) | Uses Python built-in `round()` which applies banker's rounding (round half to even) and float precision issues, violating Rule R4 (half-up rounding). | Elapsed seconds resulting in `2.675` hours rounded down to `2.67` instead of `2.68`. | Used `decimal.Decimal` with `ROUND_HALF_UP` (`Decimal(str(sec/3600)).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`). |
| 7 | Instant handling (throughout) | Fails to truncate instants to whole seconds prior to calculations per Rule R1. | Timestamps with non-zero milliseconds (e.g. 09:40:00.900) altered duration calculations and persisted fractional seconds. | Truncated epoch milliseconds to whole seconds `(punched_at // 1000) * 1000` before calculation and storage. |
| 8 | `create_employee` (lines 78-85) | Check-then-insert race condition. Uses `find_one()` followed by `insert_one()`. | Two simultaneous `POST /employees` with identical `emp_code` both passed `find_one` and caused unhandled `DuplicateKeyError` (500). | Relies on unique index on `emp_code`, catching `pymongo.errors.DuplicateKeyError` to return HTTP 409 Conflict. |
| 9 | `create_employee` (line 82) | Stores and returns `created_at` as naive local datetime instead of UTC BSON date in DB and epoch milliseconds in API response. | Response returned ISO timestamp string instead of integer epoch milliseconds, failing OpenAPI validation. | Saved as UTC datetime in MongoDB and serialized to integer epoch milliseconds in API output. |
| 10 | `EmployeeIn` model (lines 53-61) | Missing contract validations: no regex for `emp_code`, and does not reject identical `shift_start` and `shift_end`. | Creating an employee with `shift_start: "09:00"` and `shift_end: "09:00"` succeeded with 201 instead of 422. | Added regex `^EMP\d{4,6}$` and a model validator ensuring `shift_start != shift_end`. |
| 11 | `list_employees` (line 93) | Pagination calculation off-by-one: `skip = page * page_size`. | Requesting `page=1` skipped the first 20 records (pages 1 and 2 returned records 21-40 and 41-60). | Fixed skip calculation to `(page - 1) * page_size`. |
| 12 | `list_employees` (line 94) | `total` count ignores active filters, running `count_documents({})` across all employees. | Querying `GET /employees?department=Sales` returned `total` as total collection size rather than sales headcount. | Changed to `db.employees.count_documents(q)` to accurately reflect the filtered query. |
| 13 | `list_employees` (line 95) | Missing sort requirement. OpenAPI mandates sorting by `emp_code` ascending. | Returned documents in non-deterministic natural database insertion order. | Added `.sort("emp_code", 1)` to the MongoDB query cursor. |
| 14 | `punch_in` (line 101) | Does not handle non-existent employee; directly indexes `emp["shift_start"]`. | Calling `POST /attendance/punch-in` with an unknown employee caused `TypeError: 'NoneType' object is not subscriptable` (500). | Added check: `if not emp: raise HTTPException(404, "Employee not found")`. |
| 15 | `punch_in` (lines 102-103) | Fails to detect overnight shift attendance date per Rule R1. Simply uses current date. | Punch-in at 01:00 IST for a 22:00-06:00 shift was assigned to today's date instead of yesterday's shift start date. | Implemented R1 logic: if `shift_end <= shift_start` and punch-in IST time `< shift_end`, attendance date is `ist_date - 1 day`. |
| 16 | `punch_in` (lines 104-105) | Check-then-insert race condition. Two simultaneous punch-ins for the same day can both pass `find_one`. | Concurrent requests created duplicate records or unhandled 500 error. | Enforced compound unique index `(emp_code, date)` and caught `DuplicateKeyError` to return HTTP 409. |
| 17 | `punch_in` / `list_attendance` (lines 119, 149) | Returns internal `id: str(_id)` in response body. OpenAPI and DATA_MODEL state attendance records have no ID. | Response payload contained extraneous `"id"` field failing OpenAPI contract schema validation. | Removed `doc.pop("_id", None)` and omitted `"id"` entirely from responses. |
| 18 | `list_attendance` (lines 144-147) | Severe scalability defect. Fetches entire collection into memory with `list(db.attendance_logs.find(q))` and sorts in Python. | On 100,000 documents, caused massive memory consumption, latency spikes, and server timeouts. | Replaced with MongoDB cursor chaining: `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)`. |
| 19 | `list_attendance` (lines 127-128) | Missing validation for date range. If `date_from > date_to`, contract specifies HTTP 422. | Calling `?date_from=2026-07-10&date_to=2026-07-01` returned 200 with empty items rather than 422. | Added validation raising HTTP 422 when `date_from > date_to`. |

## Items examined and determined NOT to be defects
1. **Reading environment variables with defaults (`os.getenv("MONGO_URI", "mongodb://localhost:27017")`):** This is intentional and compliant with Section 4 of the problem statement. When the automated grader injects custom `MONGO_URI` and `MONGO_DB` environment variables, `os.getenv` prioritizes them while providing convenient local fallback.
2. **Pydantic schema definitions:** Using Pydantic models for request body deserialization and input validation is idiomatic FastAPI practice and ensures clean request parsing.
